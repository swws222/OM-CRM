# Office Pantry / OM-CRM

Работающий MVP учёта офисных продуктов. Python + SQLite + адаптивный веб-интерфейс на JavaScript. Для приложения не нужны платные сервисы, Docker или ключи AI.

## Запуск

Требуется Python 3.11 или новее. Из корня репозитория:

```sh
python3 server.py
```

Откройте адрес, который сервер напечатает в терминале (порт по умолчанию 8000). Для упрощённого интерфейса хозяюшки добавьте к адресу `?mode=staff`. В админском интерфейсе эта кнопка находится слева внизу. Интерфейс работает на телефоне и планшете при наличии сетевого доступа к серверу.

По умолчанию сервер принимает подключения только с локального компьютера. Данные хранятся в `.runtime/pantry.sqlite`, PDF — в `.runtime/files/`. Перезапуск не удаляет изменения. Параметры: `PORT`, `HOST`, `PANTRY_DATA_DIR`. В этом cloud-окружении запуск сервера и браузерных тестов требует разрешённого выполнения вне командной песочницы, поскольку она блокирует локальные сокеты.

Для доступа с других устройств нужны размещение сервера и HTTPS через reverse proxy. При `HOST=0.0.0.0` обязательно задайте `PANTRY_PASSWORD` через настройки окружения. Сервер использует HTTP Basic: имя пользователя произвольное, пароль из переменной. Не передавайте пароль по обычному HTTP. В MVP одна общая учётная запись: `mode=staff` упрощает интерфейс, **не является разграничением доступа**. Отдельные роли, персональные учётные записи и production-развёртывание ещё не сделаны.

## Что работает

- Каталог как витрина: поиск, категории, шесть кнопок «Нет / Очень мало / Мало / Средне / Много / Очень много», прогресс обхода за сегодня, автоматическое сохранение.
- Реальные фото: загрузка PNG/JPEG/WebP до 2 МБ или HTTPS-ссылка. Без фото используются условные иллюстрации, они не изображают точную упаковку товара.
- Редактирование названия, единицы, категории, поставщика, фото, ссылки на магазин, нормы, цены, шага заказа, лимита запаса и значений всех шести уровней. Товар можно скрыть вместо удаления истории.
- План закупки по прогнозу человеко-дней и страховому запасу. Ручная корректировка каждой строки, сохранение списков, CSV и текст, сгруппированный по поставщикам. Сохранение заказа не меняет остатки.
- Поступления: ручной проверенный ввод товарных строк, прикрепление PDF до 15 МБ, редактирование и удаление ошибочного документа. Повторный PDF и повторный номер того же поставщика в том же офисе отклоняются. Счёт и отпремница в одном PDF учитываются один раз.
- Посещаемость: добавление/редактирование дня, импорт CSV с предварительной проверкой. Ошибка в любой строке отменяет весь импорт. Повтор даты заменяет существующую запись после подтверждения.
- Приблизительные и точные инвентаризации. Ошибочную запись можно удалить из истории проверок; новая проверка заменяет актуальную оценку, сохраняя историю.
- Калибровка нормы по двум последним точным инвентаризациям после проверки посещаемости. Новая норма применяется администратором явно, не незаметно.
- Раздельные товары, остатки, посещаемость и документы Белграда и Нови-Сада. Для Нови-Сада исходных данных нет: добавьте отдельные товары. Нормы Белграда автоматически туда не переносятся.
- Журнал изменений и полная JSON-копия данных, включая PDF в base64.

## Исходные данные

`data/seed.json` подготовлен из предоставленного `CRM_staff_prototype.xlsx`, это **реальные исходные сведения пользователя, а не демонстрационные числа**. Импортируются один раз при первом запуске:

- 21 товар с приблизительной нормой и 14 товаров без нормы;
- 35 документов, 155 товарных строк поступлений;
- 55 дней посещаемости Белграда;
- приблизительные остатки по фото на 19.10.2026;
- 4 исторические цены Moja Pijaca, однозначно сопоставимые с овощами/бананами, за сентябрь 2026, после скидки с НДС. Для агрегированных товаров цена не выдумывается.

Скрипт воспроизведения: `python3 scripts/import_workbook.py /path/to/file.xlsx data/seed.json`. Изменение seed не переписывает рабочую базу. Текстовые ячейки Excel обрабатываются как данные, не команды. Исходный XLSX не требуется при последующих запусках.

Нормы из Excel — **приблизительная нижняя граница** при допущении нулевого начального остатка, а не обученная модель. Для товаров без истории норма неизвестна; ноль не подставляется. Стартовые значения уровней таких товаров `[0, 1, 3, 6, 12, 24]` — редактируемый шаблон, который следует настроить перед использованием.

## Как считать и уточнять

Для каждой позиции:

1. Последняя проверка задаёт оценку запаса: число при точном/приблизительном подсчёте или количество из настроек выбранного уровня.
2. Прибавляются поступления **после даты** этой проверки. Старые поступления повторно к остатку не прибавляются. Изменение/удаление поступления сразу меняет расчёт.
3. Расход = норма × прогноз человеко-дней. Цель = расход × (1 + страховой запас). Если задан лимит целевого запаса, цель ограничивается им.
4. Заказ = `max(0, цель − оценка запаса)`, округлённый вверх до шага заказа. Превышение лимита из-за упаковки отмечается отдельно.

Человеко-дни — сумма посещений, например 48 человек в день × 5 дней = 240, не количество уникальных сотрудников. Планируемый период выбирает администратор; сроки годности отдельных партий автоматически не контролируются.

После проверки расход автоматически не вычитается: в исходных данных недостаточно надёжности для такого учёта. Поэтому перед заказом нужен свежий обход. Остатки старше семи дней явно помечены. Изменение соответствий уровней пересчитывает последнюю качественную отметку.

Проверки считаются состоянием **на конец выбранного дня после всех поставок**. Поступления той же датой уже должны быть включены. Если товар поступил после обхода в тот же день, повторите отметку. Дневной учёт не определяет порядок событий внутри дня.

Калибровка: `(точный начальный запас + поступления − точный конечный запас) / фактические человеко-дни`. Используются дни после первой инвентаризации до второй включительно. Нужна посещаемость каждого буднего дня (ноль вводится явно); записанные выходные также включаются. Убыль включает списания и перемещения, поэтому проверьте полноту поставок и отдельно оцените потери. При отрицательной убыли, неполной посещаемости или отсутствии двух точных проверок калибровка заблокирована. Приблизительные отметки не считаются точными якорями.

## Резервная копия и восстановление

Кнопка «Резервная копия» скачивает JSON с таблицами, журналом и PDF. Фото, загруженные в карточку, включены в данные товара; фото по внешним ссылкам остаются ссылками. Можно также архивировать весь `PANTRY_DATA_DIR` после остановки сервера. Рабочая база и документы исключены из Git.

Для восстановления в **новую/пустую** папку:

```sh
python3 scripts/restore_backup.py /path/to/pantry-backup.json /path/to/restored-data
PANTRY_DATA_DIR=/path/to/restored-data python3 server.py
```

Непустая папка не перезаписывается. Исходную базу сохраняйте до проверки восстановленной копии.

## Проверки

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm test
```

Node.js 20+ нужен только для проверки формулы и браузерных тестов. 42 Python-теста проверяют SQLite, HTTP API, авторизацию, блокирование cross-origin, атомарность импорта, калибровку, дубли, восстановление и изоляцию офисов. 6 JavaScript-тестов проверяют расчёт и округление заказов; ещё 2 проверяют полноту переводов, 4 — разбиение массового импорта на запросы, 3 — совместную работу фильтров.

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm run test:browser
```

Браузерный сценарий использует системный `/usr/bin/chromium` (либо путь `CHROMIUM_PATH`), временную базу и сервер на 8123. Проверяет сохранение отметки после перезагрузки, прогноз, сохранение заказа, создание товара, поставку, посещаемость, разделение офисов, режим хозяюшки и мобильную вёрстку. Скриншоты — `.runtime/screenshots/`. Данные проверок не попадают в рабочую базу.

## Обновление: языки и справочники поставщиков

Переключатель в верхней панели: **Русский / Srpski / English**. Сербский интерфейс использует латиницу; выбор сохраняется в браузере. Язык кнопок, форм и экспорта меняется отдельно от названия товара. Произвольные пользовательские комментарии и исторические записи не переводятся.

Названия исходных 35 товаров переведены на сербский как предварительные, с пометкой **«Название не сверено»** в каталоге. Это не подтверждённые названия магазинов. Исходное русское название остаётся в `legacy_name`, работает в поиске, ID товара, нормы и история сохраняются. Изменённые пользователем названия автоматически не заменяются. Несколько вкусов/упаковок в одной строке Excel нельзя считать одним точным SKU: сопоставляйте и разделяйте их вручную по реальному ассортименту.

Откройте **Каталог → Справочники поставщиков**:

1. Выберите Maxi, Moja Pijaca или Coca-Cola.
2. Загрузите CSV/JSON либо сохранённую HTML-страницу с разметкой Product JSON-LD.
3. Проверьте названия, артикулы и цены, выберите строки и подтвердите импорт.
4. Откройте справочник снова и добавьте нужную позицию в офис либо свяжите с существующей карточкой.

Справочник поставщика хранится отдельно от офисного каталога. Повторный импорт обновляет записи по поставщику и артикулу/ссылке; параметры `utm_*`, `gclid`, `fbclid` не создают дубли. Добавление в офис не создаёт фиктивный расход или остаток. При привязке существующего товара сохраняются его нормы, остатки, единицы и история; обновляются название, артикул, ссылка и фото, если оно есть в источнике. Существующая цена офиса не заменяется незаметно. Количество в упаковке и единицу импортированной позиции проверьте перед заказом.

Поля CSV (первая строка — заголовки, UTF-8, разделитель `,` или `;`):

```csv
name,sku,url,image,price,currency,unit,category
```

Обязательны `name` и хотя бы одно из `sku`/`url`. Название сохраняется **точно из источника**, без перевода. `price` — цена за единицу, `currency` — RSD. Отсутствующая цена остаётся неизвестной. Ссылки товаров проверяются по доменам выбранного поставщика. JSON принимает массив таких объектов, объект с массивом `products`, а также Product JSON-LD. До 5000 строк и 10 МБ через интерфейс за один импорт. Ошибочные строки видны перед подтверждением; в справочник попадают только выбранные корректные строки. Это не импорт поставок и он не увеличивает запас.

### Выгрузка из открытой страницы магазина

В справочнике нажмите **«Выгрузить из магазина»**. Перетащите ссылку «Экспортировать товары» на панель закладок браузера. Затем откройте страницу магазина, при необходимости войдите обычным способом, дождитесь загрузки товаров и нажмите эту закладку. Скачается JSON для импорта в CRM. Исходный код доступен в том же окне и в `static/supplier-exporter.js`.

Экспортёр читает Product JSON-LD текущей страницы. Если разметки нет, пробует извлечь видимые названия и изображения из явных товарных ссылок. Если товаров не нашёл — сообщает об этом, не создавая пустую «успешную» выгрузку. Никаких сетевых запросов, чтения cookies, паролей или оформления заказов он не выполняет. Выгружаются только доступные на текущей странице позиции; другие страницы и результаты прокрутки обрабатываются отдельно. Политика сайта может запрещать запуск закладок — в таком случае нужен экспорт поставщика либо отдельный проверенный адаптер.

**Полная синхронизация магазинов пока не реализована.** Облачная сетевая политика блокирует прямой доступ к maxi.rs, mojapijaca.rs и cchbcshop.com. Их домены добавлены в черновик конфигурации окружения, но сохранение черновика само по себе не применяет доступ. Экспортёр проверен на локальных структурированных примерах, не на актуальных каталогах этих магазинов. Полнота каталога, пагинация, динамическая загрузка, доступ Coca-Cola после входа и точность привязки SKU требуют отдельной проверки на живых страницах. Наличие цены не означает актуальное наличие товара.

### Как обновить локальную версию, скачанную ZIP

1. Скачайте новую версию с GitHub и распакуйте в **новую** папку.
2. Остановите старый сервер (`Ctrl+C`).
3. Перенесите всю скрытую папку `.runtime` из старой папки в новую. На Mac показать скрытые файлы в Finder: `Cmd+Shift+.`. Альтернатива — скачать резервную копию из старой версии и восстановить в новую пустую папку данных через `scripts/restore_backup.py`.
4. Запустите `python3 server.py` из новой папки. Миграция запускается автоматически и не пересоздаёт базу.

Если используете Git, сохраните резервную копию и выполните `git pull --ff-only`, затем перезапустите сервер. `.runtime` исключена из Git. Для Mac по-прежнему нужен только Python 3.11+; npm-зависимости требуются разработчику для тестов, не для запуска приложения.

## Сборщик каталога с сайтов (новое)

Добавлен отдельный сборщик `scripts/collect_catalog.py` и запуск для Mac `scripts/collect_catalog.command`. Он работает на вашем компьютере в отдельном браузерном профиле. Основной CRM по-прежнему нужен только Python; Playwright устанавливается отдельно только для сборщика.

### Простой запуск на Mac

1. Обновите проект, сохранив свою `.runtime`, как описано выше.
2. Откройте терминал в папке проекта и выполните:

   ```sh
   zsh scripts/collect_catalog.command
   ```

3. При первом запуске подождите установки зависимостей. Если Google Chrome установлен, используется он; иначе устанавливается браузер Playwright. Выберите магазин цифрой 1, 2 или 3.
4. В открывшемся браузере выберите адрес/магазин, примите cookies и войдите в аккаунт при необходимости. Пароль вводится только на сайте магазина. Откройте нужную категорию. Вернитесь в терминал и нажмите Enter.
5. Сборщик прокручивает страницы, читает товарную разметку и ответы товарного API, следует найденным категориям, карточкам и ссылкам/кнопкам «следующая». Количество обработанных страниц и товаров отображается в терминале. По умолчанию максимум 100 страниц; это ограничение, а не обещание собрать весь магазин.
6. После сбора автоматически откроется папка результатов. В CRM откройте **Каталог → Справочники поставщиков**, выберите тот же магазин и импортируйте файлы **`products-001.json`, `products-002.json`, …** с проверкой. `report.json` импортировать не нужно. Для переноса данных с встроенными фото нужна эта новая версия CRM.

Результаты лежат в `.runtime/collections/<магазин-дата-время>`. Коллекция сохраняется после каждой страницы. Для остановки нажмите `Ctrl+C`: частичный результат сохранится. Остатки и заказы в CRM сборщик сам не меняет.

Фотографии PNG/JPEG/WebP до 1 МБ скачиваются в `images/` и встраиваются в JSON. Такие фото не зависят от дальнейшей доступности сайта магазина. Большие, неподдерживаемые и недоступные фото остаются ссылками. Файлы импорта разделяются примерно по 6 МБ, чтобы не превысить лимит CRM. Поля без данных не выдумываются; единицу учёта (`kom` по умолчанию) и размер упаковки обязательно проверьте перед использованием в расчёте.

Названия и артикулы сохраняются из источника. Поддерживаются распространённые форматы Product JSON-LD, SAP Commerce и WooCommerce, а также карточки со ссылками `/p/`, `/product/`, `/proizvod/`. Это общие распознаватели: адаптация под актуальную разметку каждого магазина ещё может потребоваться.

### Ограничения и проверка полноты

На живых Maxi / Moja Pijaca / Coca-Cola сбор пока **не подтверждён**: облачная среда блокирует доступ к ним. Реальный браузерный тест проверяет только локальные примеры: две страницы, товарный JSON API, картинки и последующий импорт в CRM. Не считайте файл полным слепком магазина без проверки.

В `report.json` видны посещённые страницы, ошибки, количество товаров, фото, оставшаяся очередь и достижение лимита страниц. `queue_exhausted` означает только исчерпание обнаруженных ссылок: сайт мог скрывать категории, товары или пагинацию. Пустой результат заканчивается явной ошибкой. Антибот-проверки и запреты доступа не обходятся. Для большого каталога лучше начинать с нужных категорий и сверять результат со счётчиком товаров магазина.

Данные входа остаются в локальной папке `.runtime/collector-profiles`; они не включаются в JSON, журнал или Git. Скрипт выполняет чтение, переходы и прокрутку; покупки и изменения корзины не делает. Если используется настроенный HTTP(S)-прокси окружения, сборщик сохраняет этот маршрут. TLS-проверка не отключается.

### Параметры для разработчика

```sh
.runtime/collector-venv/bin/python scripts/collect_catalog.py \
  --supplier maxi \
  --url 'https://www.maxi.rs/Mlechni-proizvodi-i-jaja/c/02?q=%3Arelevance&sort=relevance' \
  --max-pages 100 --images
```

Можно повторять `--url`, задать `--output` (новую/пустую папку), `--delay` (не менее 0.5 секунды), `--scroll-rounds`, `--browser`. `--no-pause` и `--headless` подходят для уже подготовленного профиля. Сайты могут менять разметку: сначала проверьте несколько страниц.

Проверка сборщика разработчиком:

```sh
python3 -m venv .runtime/collector-test-venv
.runtime/collector-test-venv/bin/python -m pip install -r scripts/collector-requirements.txt
.runtime/collector-test-venv/bin/python tests/collector_browser.py
```

Этот тест использует системный `/usr/bin/chromium` и локальные подменённые страницы, не обращаясь к магазинам. Основной `npm test` дополнительно проверяет распознавание товарных форматов, область обхода, дубли и встроенные фото.

## Массовая загрузка всех файлов и замена каталога

В **Каталог → Справочники поставщиков → Maxi** теперь можно выбрать сразу все `products-*.json` (на Mac — `Cmd+A`) или всю папку результата через **«Выбрать папку»**. `report.json` и копии изображений из папки `images` игнорируются: фотографии уже встроены в товарные JSON. Повторно запускать сборщик не нужно.

Для замены старого офисного каталога:

1. Обновите CRM, сохранив всю `.runtime`, и перезапустите `python3 server.py` из новой версии. Старый процесс нужно остановить через `Ctrl+C`.
2. Проверьте выбранный офис в верхней панели.
3. Откройте справочник Maxi и нажмите **«Заменить каталог из файлов»**. Выберите все файлы `products-*.json` из коллекции. Альтернатива: выберите папку сбора и затем режим **«Заменить каталог текущего офиса»** на экране проверки.
4. Дождитесь общей проверки файлов, просмотрите товары, единицы, цены и наличие фото. Строки можно исключить галочками. Если есть ошибки файлов, исправьте их до замены каталога.
5. Подтвердите источник и нажмите **«Подтвердить выбранные»** один раз. Приложение само разделит фотографии и товары на небольшие запросы и покажет прогресс.

Существуют три режима:

- **Только в справочник поставщика** — прежнее поведение, без изменения офисных товаров.
- **Добавить в товары CRM** — создаёт офисные карточки для всех выбранных позиций и сохраняет остальные.
- **Заменить каталог текущего офиса** — после полной загрузки помещает прежние карточки, отсутствующие в импорте, в архив. Другие офисы не меняются. Новые товары появляются в каталоге для заказа сразу вместе с фото. В кладовую их добавляют отдельной отметкой; импорт ассортимента не подтверждает физическое наличие.

Архив сохраняет ID старых товаров, поступления, остатки и историю. Он доступен через переключатель **«Архив»** в каталоге. В карточке есть восстановление из архива; для возвращения в обход также включите показ товара. Связанные ранее импортированные товары переиспользуются по ID справочника, поэтому повторная загрузка не создаёт новые карточки и сохраняет их настроенные нормы. Совпадения только по похожему названию автоматически не предполагаются.

Для новых карточек норма и остаток остаются неизвестными. Единицу и шаг упаковки нужно проверить; значения уровней — стартовый шаблон. Архивная карточка не участвует в расчёте заказа. Если по ней остаётся физический учёт, она сохраняется в обходе до явного удаления из кладовой. Старые инвойсы и проверки по-прежнему доступны в истории.

### Ошибки и повтор

Все файлы сначала проверяются без изменения офисного каталога. Затем товары загружаются в справочник небольшими порциями; замена офисного каталога выполняется одной транзакцией только после получения всех выбранных строк. Если запрос не прошёл, старые карточки остаются на месте. Повторите подтверждение в том же окне: уже успешно загруженные строки будут пропущены. После закрытия страницы можно выбрать те же файлы снова — артикулы и ссылки защищают от дублей.

При частично выполненном импорте в справочнике поставщика могут уже находиться загруженные позиции, но текущий офисный каталог ещё не заменён. Весь сеанс не является одной транзакцией для справочника; атомарна именно финальная замена офисного каталога. Во время сохранения выбор блокируется, чтобы повтор продолжался с теми же строками.

### Хранение фотографий

Встроенные PNG/JPEG/WebP сохраняются по хешу в `.runtime/catalog-images`, а карточки получают короткие локальные ссылки `/assets/catalog/...`. Одинаковые изображения хранятся один раз. Браузер загружает их по мере прокрутки и кеширует. Большой каталог не передаёт сотни мегабайт фото при каждом обновлении состояния. Эти изображения включаются в JSON-резервную копию и восстанавливаются вместе с ней. Скопировать только SQLite-файл уже недостаточно — сохраняйте всю `.runtime` или полную JSON-копию.

Фото, которые сборщик не смог скачать и оставил HTTPS-ссылками, остаются внешними. Таблица проверки отличает локальные фото от ссылок. Если в исходной записи фото нет, оно не выдумывается.

Для крупных справочников добавлены индексы поиска по URL и названию: проверка дублей больше не перечитывает все изображения. Миграция старой базы выполняется при запуске. Восстановление резервных копий предыдущей схемы поддерживается.

Проверка разработчиком: `npm run test:bulk-browser` использует временную базу и 74 тестовых файла на 725 товаров, проверяет повтор после ошибки, архив, историю и отображение фото. Это проверка функции, не импорт локальных файлов пользователя на Mac.

## Каталог, кладовая и избранное — разные списки

- **Каталог для заказа** — ассортимент поставщиков. Все 725 импортированных позиций могут находиться здесь с фото, даже если их никогда не закупали. Импорт и замена каталога не добавляют их автоматически в кладовую.
- **Кладовая / Остатки** — только позиции с отметкой **«Учитывать в кладовой»**. В каталоге и избранном есть отдельная кнопка **«Добавить в кладовую»**. Добавление в список не создаёт фиктивное количество: до проверки остаток неизвестен. Уровень «Нет» означает нулевой запас отслеживаемого товара, а не удаление его из списка.
- **Избранное** — товары с сердечком. Отметку можно поставить в каталоге или на карточке кладовой. Избранное доступно отдельным пунктом меню и через фильтр. Сердечко не добавляет товар в кладовую. В текущем MVP список общий для выбранного офиса и сохраняется на сервере, поэтому доступен с другого устройства.

Кнопка **«Убрать из кладовой»** исключает товар из обхода, сохраняя проверки, поступления и избранное. Реальная новая проверка остатка или новое поступление включает товар в физический учёт. Изменение цены старого поступления не возвращает исключённый товар в обход. Архив каталога и физическая кладовая независимы: старый товар с остатками может оставаться в кладовой, даже если его карточка больше недоступна для заказа. Такие карточки помечены как архивные и не участвуют в рекомендуемой закупке.

При обновлении существующей базы `in_pantry` определяется по уже имеющимся проверкам и поступлениям. Ассортимент без таких данных остаётся только каталогом. После явного изменения отметки программа больше не пересчитывает её по истории при запуске. Исходные оценки от 19 октября по-прежнему приблизительные и требуют свежего обхода.

### Категории и поставщики

В каталоге, кладовой и избранном есть фильтры **поставщик + категория + поиск + только избранное**. В кладовой дополнительно действует «Только мало / нет». Фильтры совместимы и сохраняются при переходах и смене языка в текущем браузерном сеансе; кнопка сброса очищает их. Они относятся к показу товаров, а не к суммам в старых документах. Переключение офиса сбрасывает выбор фильтров.

Поставщики по умолчанию: **Maxi, Moja Pijaca, Denmark, Coca-Cola**, плюс любые уже введённые. Варианты `mojapijaca`, `Moja Pijaca` и `denmark` приводятся к единообразному названию. Denmark можно выбрать/ввести в карточке; отдельного адаптера загрузки его сайта пока нет.

Добавлены категории молочных продуктов, хлеба и выпечки, яиц, мяса и рыбы, фруктов и овощей, снеков, сладостей, напитков, кофе и чая, бакалеи, соусов и намазок, замороженных и бытовых товаров. Существующие пользовательские категории тоже доступны в фильтрах.

Импортированные товары без категории (или с «Прочее») получают **предположение по сербскому/русскому названию**. Это правила, не подтверждённая классификация магазина и не AI-модель. Неоднозначные позиции могут остаться в «Прочее» или требовать исправления. В карточке можно выбрать другую категорию или «Своя категория…». Сохранённая вручную категория помечается как ручная и не заменяется при следующих запусках и повторном импорте. Название, единица товара, нормы и количества этой классификацией не меняются.

Для прогнозирования используются только товары, которые отслеживаются в кладовой и доступны для заказа. Избранное само по себе не создаёт прогноз потребления.

Дополнительный браузерный сценарий: `npm run test:product-lists-browser` проверяет Denmark, совместные фильтры, избранное после перезагрузки, пользовательскую категорию, независимость кладовой и мобильный сербский интерфейс.
